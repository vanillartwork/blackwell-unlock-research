## 结论摘要

| 问题 | 结果 |
|---|---|
| `80 + 高16位(+18) × 低16位(+1C) + stored_size = 对象长度` | **72 / 72 成立**，覆盖全部五个核心 |
| 清单 `entry_id` 就是目录对象编号 | **132 / 132 成立**（120 相等，12 为 `0x14` 的前缀） |
| EFI 载荷的分组跟着固件代次，不跟着核心 | **得到事前预测的验证**：`98.03.3B` 的 5070 Ti 与同版本 5080、`98.02.2E` 的 5090 同组，`98.03.58` 的 5070 Ti 在另一组；GB202 与 GB203 各跨两组 |
| APP `0x24` 在同一代内跨核心相同 | **被 5090 D 推翻**（八份样本时的结论）：5090 D、PRO 6000、5070 的 EFI 载荷各有同组，APP `0x24` 却自成一组 |
| `0x2B80` 镜像全系相同 | **不成立**。EFI 载荷、APP `0x24`、APP `0x18` 都有跨核心共用的例子，但没有一个在五个核心上全部相同 |
| 华硕与同德的桌面 RTX 5070（均为 `98.05.28.00`，末段 OEM 版本号不同） | 6 个描述符、载荷、尾部及两份清单均相同。140 个板卡对象中有 17 个不同，其中 13 个在 5080 与 5070 Ti 之间也不同。 |
| 核心本身能决定微码载荷 | **不能**。同为 GB205，5070 与笔记本的 6 个载荷全部不同，只有 EFI 载荷相同 |
| RTX PRO / 5090 D 与其他卡的结构差别 | **未发现**：对象编号、槽位、APP、标志位与常量全部相同；载荷不同，但产品与版本同时变了，无法归因 |
| 只有笔记本不同的对象 | 6 个（`0x5f` `0x61` `0x62` `0x65` `0x7d` `0xe4`）在十一份桌面 / 工作站 ROM 上完全相同，**包括桌面 GB205**，因此不属于 GB205 核心；属于移动版、该产品还是 `98.05.31` 版本未定 |
| `0x7a` `0x7b` `0x7c` 缺失 | 桌面 GB205、GB206、GB207 缺失；GB205 笔记本有且更长，因此**不跟着核心** |
| 28 字节尾部 | 与载荷一一对应（51 对 51），不是所试范围的普通摘要；清单源数据改变时它不变 |
| `desc+08` 是 T 空间基址 | **被推翻**；它等于 APP `0x18` 的 `+0C`（12 / 12） |
| 外层 `+00C` 的含义 | 未定。**线索**：四个小对象（`0x52` `0x5c` `0x74` `0x76`）的两种内容与它的两个取值完全同步（12 / 12），等下一份 ROM 检验 |

## 复现

```bash
python3 scripts/rom-survey.py /path/to/roms --export rom-survey.json --v6-dir v6
python3 scripts/v6-closure.py reports/rom-survey-20261123/v6-descriptors-98.02.2E.80.C8.json
```

分组字母按命令行给出的 ROM 顺序排列；本归档的顺序与上表一致。

- 内容相同的文件只计一次，重复的会被提示并跳过，不能当作第二份样本。
- 只有对象哈希与目录摘要**全部**校验通过、其余检查也成立，结论才是 `ok`。摘要分 `verified`、`mismatch`（有值但不符）与 `absent`（没有可比的值）三种；`hashes_failed` 列出未通过的对象编号。
- `v6_file` 是该 ROM 的标量文件名。版本号相同的不同 ROM 会在文件名后附上 ROM SHA-256 的前 12 位。本归档中 GB205 笔记本的那份存放在 [gb205-2f18](../gb205-2f18/README.cn.md)，其余在本目录。
